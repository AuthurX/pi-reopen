# pi-reopen — восстановление сессий Pi в WezTerm

[English](README.md) · [简体中文](README.zh-CN.md) · [日本語](README.ja-JP.md) · [한국어](README.ko-KR.md) · [Deutsch](README.de-DE.md) · [Français](README.fr-FR.md) · [Español](README.es-ES.md) · [Português (BR)](README.pt-BR.md) · [Русский](README.ru-RU.md) · [Пакет Pi](https://pi.dev/packages/@ellieyujin/pi-reopen) · [Релизы](https://github.com/AuthurX/pi-reopen/releases)

**Перезапустите WezTerm. Восстановите сессии агента кодирования Pi, рабочие каталоги и диалоги одной командой.**

![Pi session recovery preview](https://raw.githubusercontent.com/AuthurX/pi-reopen/main/assets/preview.png)

Расширение и CLI для [Pi](https://github.com/earendil-works/pi) — **восстановление сессий после закрытия терминала**. Запоминает открытые сессии Pi и открывает их снова как вкладки [WezTerm](https://wezterm.org/), пропуская уже запущенные сессии.

## Возобновить одну сессию или восстановить рабочее пространство?

| Задача | Что использовать |
| --- | --- |
| Продолжить последнюю сессию в текущем каталоге | Встроенный `pi -c` |
| Выбрать прошлый диалог | Встроенный `pi -r` или `/resume` |
| Снова открыть зарегистрированные сессии Pi между проектами после закрытия WezTerm | `pi-reopen` |
| Просмотреть план восстановления без открытия вкладок | `pi-reopen restore --dry-run` |

Это **восстановление сессий рабочего пространства**, а не замена выборщику сессий Pi. Запускаются новые процессы Pi с исходными файлами сессий; работающие инструменты, несохранённое состояние, геометрия разделённых панелей и произвольные shell-программы не восстанавливаются. Осознанное выход из Pi удаляет его запись. Запуск WezTerm не запускает восстановление автоматически; запустите `pi-reopen` после повторного открытия.

## Как пользоваться: представьте вкладки браузера

| Браузер | pi-reopen |
| --- | --- |
| Вкладки, открытые при выходе | Сессии Pi, открытые при закрытии WezTerm |
| Открытые вкладки возвращаются при следующем запуске | `pi-reopen` восстанавливает сохранённые записи как новые вкладки |
| Закрытые вами вкладки не попадают в список восстановления | Закрытая с `ctrl+w` вкладка по умолчанию забывается (всегда — при `/quit` внутри Pi) |
| «Недавно закрытые» через Ctrl+Shift+T | `/reopen recent` — последние 24 ч, даже без записи |
| Сбой → «Восстановить страницы?» | Сбой / закрытие всего WezTerm / выключение WSL → все записи сохраняются, `pi-reopen` возвращает их |

Правило, которое нужно запомнить: **открыто = оставляем, закрыто = отпускаем**. Без маркеров и дополнительных команд — оставленная открытой вкладка — это сигнал «я хочу её вернуть», а закрытая — «я закончил с ней». (По умолчанию: закрытая вкладка удаляется из списка восстановления, как в браузере; задайте `PI_REOPEN_FORGET_ON_TAB_CLOSE=0`, чтобы всегда сохранять записи.)

## Сценарий использования и поддержка платформ

**Создано для работы над несколькими проектами в WezTerm: у вас открыто несколько сессий Pi, вы закрываете терминал и хотите вернуть зарегистрированные сессии с их рабочими каталогами и диалогами.** Снова откройте WezTerm и запустите `pi-reopen`, чтобы восстановить ожидающие сессии в новых вкладках.

| Окружение выполнения | Статус поддержки | Где открываются сессии |
| --- | --- | --- |
| Нативный Linux | Реализовано | Новые вкладки в локальном WezTerm на Linux |
| Нативный macOS | Реализовано | Новые вкладки в локальном WezTerm на Mac |
| Нативный Windows | Реализовано | Новые вкладки в локальном WezTerm на Windows, с нативным Windows-Pi |
| WSL | Реализовано | Новые вкладки в WezTerm для Windows, запуск Pi в соответствующем дистрибутиве WSL |
| FreeBSD и другие ОС | Не поддерживается | Предполёт восстановления отклоняет неподдерживаемые платформы |

**Единственная цель восстановления — локальный WezTerm.** Восстановление в Windows Terminal, iTerm2, встроенный терминал VS Code или tmux не поддерживается. PowerShell, Bash и zsh — это shell-с, а не целевые терминальные приложения; запуск команды из PowerShell всё равно требует открытого WezTerm. Нативный Windows и WSL — отдельные окружения: установка на одной стороне не может восстановить сессии другой. Перенос между машинами не поддерживается.

«Реализовано» означает, что существует платформенно-зависимый путь восстановления, а не что все сценарии на реальных машинах проверены. См. [заметки по платформам](docs/PLATFORMS.md) о покрытии проверки и ограничениях.

## Быстрый старт

`@ellieyujin/pi-reopen` — единственный поддерживаемый npm-пакет. Команда CLI остаётся `pi-reopen`.

```bash
pi install npm:@ellieyujin/pi-reopen@latest
npm install -g @ellieyujin/pi-reopen@latest --omit=peer
pi-reopen setup
```

`setup` объединяет проверки источника расширения, жив ли его регистрирующий процесс, глобальный CLI и PATH, согласованность версий и дублирующиеся устаревшие записи. Показывает следующие команды для платформы, но никогда не выполняет `sudo`, `setx` и не меняет системную конфигурацию.

Запустите `/reload` в каждом существующем Pi, чтобы он начал регистрацию. После закрытия и повторного открытия WezTerm:

```bash
pi-reopen restore --dry-run
pi-reopen
```

Перед сменой имени пакета ознакомьтесь с [установкой и миграцией](#установка).

## Требования

- **Linux / macOS / нативный Windows + локальный WezTerm**, либо **WSL + WezTerm для Windows**
- Node ≥ 22.19, с установленным [Pi](https://github.com/earendil-works/pi) в том же окружении ОС
- Откройте WezTerm перед восстановлением; инструмент добавляет вкладки в работающий экземпляр, а не в удалённую SSH-домен
- Linux/macOS/WSL требуют Bash. Нативный Windows требует Windows PowerShell 5.1 (включая CIM); установите Git for Windows для Bash-инструмента Pi, предпочтителен свежий WezTerm nightly
- Восстановление WSL использует пользователя дистрибутива по умолчанию; запускайте инструмент этим пользователем. Не разделяйте один реестр между нативным Windows и WSL

Версия 1.0.0 — первый стабильный релиз. CI выполняет платформенные тесты на Linux, macOS и Windows, полный набор регрессионных тестов, проверки упакованного tarball и реальный цикл жизни PTY Pi на Linux; приёмка закрытия/повторного открытия GUI на macOS/Windows всё ещё требует проверки на реальных машинах. См. [заметки по платформам](docs/PLATFORMS.md).

## Использование

```bash
pi-reopen
```

```text
  ✔ pi-workspace: запущен и подтверждён (/home/ellie/work/MY/code/pi-workspace)
  ⚠ other-proj: вкладка создана, запуск pi не подтверждён вовремя (/home/ellie/work/other-proj)
Обработано 2
```

Вывод следует локали: китайский для `zh_*`, в остальном английский. Принудительно — `PI_REOPEN_LANG=zh|en`.

| Вывод | Значение |
| --- | --- |
| `✔ запущен и подтверждён` | запущен и подтверждён |
| `⚠ вкладка создана, запуск pi не подтверждён вовремя` | вкладка создана, но подтверждение запуска pi истекло |
| `Обработано N` | обработано N |

Эквивалентные точки входа внутри Pi:

- `/reopen` — восстановить зарегистрированные Pi
- `/reopen recent` — подобрать из истории диалогов за последние 24 ч (для незарегистрированных окон)
- `/reopen clear` — очистить реестр (не удаляет файлы диалогов)
- `Ctrl+Shift+O` — восстановление в один клик

`/all` по-прежнему работает как устаревший псевдоним `/reopen` (показывает уведомление о переименовании).

## Команды

| Команда | Описание |
| --- | --- |
| `pi-reopen` (т. е. `pi-reopen restore`) | Снова открыть Pi, остававшиеся открытыми при последнем закрытии; работающие пропускаются |
| `pi-reopen restore --dry-run` | Показать только план, не открывая вкладок |
| `pi-reopen restore --no-wait` | Не ждать подтверждения запуска каждого pi |
| `pi-reopen restore --only <шаблон>` | Восстановить только совпавшие сессии (подстрока, `*`-глоб или индекс текущего списка; имя, путь или id) |
| `pi-reopen restore --interactive` | Показать текущий список и ввести индексы для выбора сессий |
| `pi-reopen restore --limit <N>` | Открыть не более N вкладок в этот запуск; остальные отложены на следующий раз |
| `pi-reopen restore --json` | Машиночитаемый вывод |
| `pi-reopen list [--wide\|--json]` | Список зарегистрированных участников и статусов; длинные содержимое по умолчанию обрезается по ширине терминала |
| `pi-reopen show <индекс\|id\|префикс> ...` | Показать состояние, пути, файл сессии и детали регистрации |
| `pi-reopen forget <индекс\|id\|префикс> ...` | Удалить конкретные записи (файлы диалогов не трогаются) |
| `pi-reopen prune [--dry-run]` | Удалить просроченные/невосстановимые записи (сохраняет последние 14 дней) |
| `pi-reopen setup` | Пошаговые проверки первого запуска; показывает команды, не меняя систему |
| `pi-reopen doctor` | Проверка окружения и реестра (идентичность процесса расширения, совпадение версий и детект закрытия одиночной вкладки WSL) |
| `pi-reopen clear` | Очистить реестр и заявки на запуск (не удаляет файлы диалогов и записи в устаревшем формате) |
| `pi-reopen --help` / `--version` | Использование / версия |

Колонка `#` — это **индекс в текущем снимке списка, а не стабильный ID**. Каждая команда разрешает его по самому свежему списку в том же порядке; после добавлений, удалений или переупорядочивания по времени запустите `pi-reopen list` снова. Чисто числовой ввод сначала трактуют как индекс; ID сессий и уникальные префиксы по-прежнему поддерживаются.

```bash
pi-reopen list
pi-reopen restore --only 1,3 --dry-run
pi-reopen show 2
pi-reopen forget 2
pi-reopen restore --interactive
```

Статусы `list`: running (выполняется) / start claimed (запуск зарезервирован) / pending restore (ожидает восстановления) / expired (просрочен) / open in another window (открыт в другом окне) / working directory missing (нет рабочего каталога) / session file missing (нет файла сессии) / не совпал с `--only` / отложен по `--limit` / другая платформа или дистрибутив / дублирующая запись.

Коды завершения: 0 успех; 1 запрос восстановления не удался или неизвестная команда; 2 не пройден предполёт окружения; 3 запросы отправлены, но не подтверждены; 4 только пропуски (зарезервировано/отложено).

## Установка

### Из npm

Используйте `@ellieyujin/pi-reopen` со стабильным dist-tag `latest`. Неймспейс-лишённый пакет `pi-reopen` снят с публикации. Неймспейс-лишённый `pi-workspace` в npm — проект другого автора.

```bash
pi install npm:@ellieyujin/pi-reopen@latest
npm install -g @ellieyujin/pi-reopen@latest --omit=peer
pi-reopen setup
```

- `pi install` регистрирует и загружает расширение, но не гарантирует, что CLI в PATH обычного shell; `npm install -g` устанавливает внешний CLI (глобальный bin-каталог npm тоже должен быть в PATH)
- CLI не зависит от peer-пакетов Pi, поэтому `--omit=peer`, чтобы не устанавливать хост; обе установки обновляются отдельно и должны оставаться на одной версии (`pi-reopen setup` / `doctor` сообщают о рассинхроне)
- `pi install` декларирует только минимальную peer-версию (`>=1.5.0`), без верхней границы: любой более новый Pi ставится напрямую

**Для регистрации нужно расширение**: установка только CLI не может записывать сессии. После установки запустите `/reload` или перезапустите каждый открытый Pi; свежая установка не может точно восстановить ранее незарегистрированные окна. Не загружайте устаревшую локальную запись расширения (например старый symlink `open-all.ts` или отдельную копию `pi-reopen`) вместе с пакетом. `pi-reopen setup` проверяет источники пакета и вероятные дубли в личном каталоге расширений; сверьте через `pi list`, отключите только старые записи и не удаляйте файлы сессий или авторизации. `doctor`/`setup` проверяет саморегистрацию по PID, времени запуска процесса и boot ID; старая `extension.json` сама по себе больше не означает, что расширение сейчас работает.

### Миграция со снятого с публикации пакета

Пользователям `@ellieyujin/pi-reopen` менять имя пакета не нужно. Если вы устанавливали теперь снятый с публикации `pi-reopen`, удалите его перед установкой поддерживаемого пакета, чтобы избежать двойной загрузки и конфликтов CLI. Проверьте `pi list` и удалите точно тот старый источник, который там показан. Для установки через `@latest`:

```bash
pi remove npm:pi-reopen@latest
npm uninstall -g pi-reopen
pi install npm:@ellieyujin/pi-reopen@latest
npm install -g @ellieyujin/pi-reopen@latest --omit=peer
```

Перезапустите Pi и выполните `pi-reopen doctor`. Файлы сессий и регистрации в `~/.pi/agent/pi-reopen/` не меняются; не удаляйте их. Версии CLI и расширения должны совпадать. Не комбинируйте локальную ссылку на расширение (например старый `open-all.ts` или symlink `pi-reopen`) с npm-пакетом.

### Из исходников

Следующие команды выполняются на Linux/macOS/WSL и устанавливают текущий проверенный исходный код:

```bash
git clone https://github.com/AuthurX/pi-reopen.git
cd pi-reopen
pi install .
mkdir -p "$HOME/.local/bin"
ln -s "$PWD/bin/pi-reopen.js" "$HOME/.local/bin/pi-reopen"
export PATH="$HOME/.local/bin:$PATH"
pi-reopen setup
```

Сохраните настройку PATH в файле инициализации shell. Если symlink CLI уже существует, сначала проверьте его цель; не переопределяйте вслепую.

В нативном Windows, из проверенного репозитория в PowerShell:

```powershell
pi install .
node .\bin\pi-reopen.js doctor
node .\bin\pi-reopen.js
```

Используйте `pi.cmd` вместо `pi`, если политика выполнения PowerShell блокирует `.ps1`-шим npm; менять политику не нужно.

Если нужно только расширение, можно напрямую установить опубликованную Git-версию:

```bash
pi install git:github.com/AuthurX/pi-reopen
```

## Необязательная конфигурация

| Переменная окружения | Назначение |
| --- | --- |
| `PI_REOPEN_WEZTERM` | Абсолютный путь локального WezTerm (`wezterm` / `wezterm.exe`); в WSL используйте его путь Windows, например `/mnt/c/Program Files/WezTerm/wezterm.exe` |
| `PI_REOPEN_PI_BIN` | Абсолютный путь исполняемого файла Pi, без аргументов; Windows принимает npm `pi.cmd`, JS-вход пакета или `.exe`; псевдонимы/функции не поддерживаются |
| `PI_CODING_AGENT_DIR` | Использовать другой каталог конфигурации/реестра Pi; CLI и расширение должны оставаться согласованными |
| `PI_REOPEN_SRC` | Только для разработки: переопределяет общий каталог `src/`; для обычных установок пакета не нужен |
| `PI_REOPEN_LANG` | Принудительный язык вывода: `zh` или `en` (по умолчанию из `LC_ALL`/`LANG`) |
| `PI_REOPEN_TERMINAL` | id адаптера терминала; реализован только `wezterm` (см. [docs/TERMINALS.md](docs/TERMINALS.md)) |
| `PI_REOPEN_MAX_AGE_DAYS` | Через сколько дней мёртвые записи перестают восстанавливаться (по умолчанию 14, `0` отключает) |
| `PI_REOPEN_FORGET_ON_TAB_CLOSE` | Закрытие одиночной вкладки (в WezTerm есть другие вкладки) считается «задача завершена» и её запись удаляется (включено по умолчанию); закрытие всего терминала или неоднозначная проверка сохраняют запись. `0`/`false` — всегда сохранять записи |

Устаревшие имена (`PI_WORKSPACE_*`) по-прежнему поддерживаются; при задании обоих каноническое имя `PI_REOPEN_*` имеет приоритет.

Например, если Pi установлен через nvm, pnpm или кастомный npm-префикс, задайте явно:

```bash
export PI_REOPEN_PI_BIN="$(type -P pi)"
export PI_REOPEN_WEZTERM="/mnt/c/Program Files/WezTerm/wezterm.exe"
pi-reopen doctor
```

На Linux/macOS/WSL Pi находится из PATH и login-окружения Bash. Нативный Windows разрешает `pi.exe` или npm `pi.cmd` из PATH; npm-шимы разрешаются в Node + точку входа установленного пакета, что избегает проблем кавычек `cmd.exe` и политики скриптов PowerShell. Нестандартные Windows-шимы требуют явной JS-точки входа или `.exe`. Восстановленные вкладки получают PATH и каталог агента вызывающего, а не полное окружение и данные авторизации. Обнаружение WezTerm проверяет платформенный PATH и распространённые места установки; только WSL использует `where.exe` + `wslpath`. Для кастомных раскладок задайте явный путь. После изменения переменных окружения перезапустите Pi; `/reload` не читает новое окружение родительского shell.

## Как это работает

![How it works](https://raw.githubusercontent.com/AuthurX/pi-reopen/main/assets/how-it-works.png)

- **Регистрация**: при каждом запуске Pi в реальном времени записывается `{абсолютный путь файла сессии, cwd, pid, processStart, bootId, paneId, weztermPid (WSL), platform, distro, user, schemaVersion}` в `~/.pi/agent/pi-reopen/members/` (один файл на сессию, атомарная замена). Записи, созданные 0.3.0 и старее под `pi-workspace/`, по-прежнему читаются и очищаются.
- **Детект закрытия**: сигнальные выходы Pi также издают событие очистки `quit`, поэтому одно имя события ненадёжно. Расширение записывает SIGHUP/SIGTERM в жизненном цикле TUI; осознанный `/quit` без сигнала или смена сессии удаляет запись; reload сохраняет запись и очищает слушателей. Без отслеживаемого сигнала также спрашивается у WezTerm, существует ли текущая панель (`WEZTERM_PANE`): исчезнувшая панель означает, что окно закрыто, запись сохраняется. По умолчанию (отключается `PI_REOPEN_FORGET_ON_TAB_CLOSE=0`) исчезнувшая панель удаляется, если в WezTerm есть другие панели (закрытие одной вкладки = задача завершена, браузерный «закрытые вкладки не входят в набор восстановления»); без других панелей или при неоднозначной проверке запись сохраняется. В WSL `list`/`restore` повторно сверяются из здорового CLI-процесса: для удаления нужны совпадающая метка сигнального закрытия, тот же зарегистрированный GUI-PID, мёртвый Pi, отсутствие исходной панели и хотя бы одна оставшаяся панель. Сбой без метки закрытия, перезапущенный WezTerm или неудачный запрос сохраняют запись для восстановления. Когда жёсткий kill мешает очистке, остаток фиксируется. При потере питания восстанавливается максимум записанные записи; последние не записанные изменения не гарантируются.
- **Безопасный запуск**: вкладки открываются параллельно (по умолчанию 5 одновременно); каждый запрос `wezterm cli spawn` прерывается ошибкой после 15 с без ответа, а 3 последовательных неудачных запроса останавливают процесс заранее, избегая долгих ожиданий при зависшем WezTerm. `--limit` ограничивает всплеск.
- **Устранение дублей**: перед восстановлением проверяется живость процессов (pid + время запуска + bootId; устаревшие PID после перезагрузки не ошибаются), работающие процессы сканируются на `--session <файл>`, чтобы незарегистрированное окно не открылось дважды, и заявки на запуск (TTL 60 с + проверка живости владельца) уменьшают дублирующиеся запросы. Глобальный замок восстановления (`restore.lock`, TTL 30 минут + живость pid + проверка bootId) создаётся с `O_EXCL`, поэтому конкурентные восстановления не могут одновременно запустить пакет; он может быть захвачен после смерти владельца замка или перезагрузки ОС.
- **Верификация**: «запрос принят» и «pi зарегистрирован» сообщаются отдельно; окно подтверждения масштабируется с размером пакета (15 с + 2 с на сессию, потолок 90 с).
- **Заголовки и гигиена**: вкладки получают заголовок с именем сессии, иначе имя папки cwd. Записи старше 14 дней помечаются `expired` и больше не восстанавливаются автоматически; `forget`/`prune` очищают, не трогая файлы диалогов.
- **Безопасность**: если предполёт (идентичность процесса / работающий WezTerm / Pi / адаптер терминала / здоровье реестра, плюс interop WSL, где применимо) не пройден, ничего не запускается пачкой; никогда никакого автосудо; ENOEXEC сопровождается подсказкой по исправлению.

## Разработка и тесты

```bash
# из корня репозитория
npm test                    # полный регрессионный набор Linux/WSL (интеграционный тест пропускается)
npm run test:platform       # нативный набор Linux/macOS/Windows
npm run verify-pack         # собрать tarball, проверить содержимое, запустить распакованный CLI
npm run test:integration    # реальный тест spawn/заголовка WezTerm (нужен работающий WezTerm)
python3 test/pty-shutdown.py # реальный PTY Pi: сигнал сохраняет запись, /quit удаляет
```

```text
extensions/index.ts      расширение Pi (тонкий адаптерный слой): регистрирует живые Pi, даёт /reopen
src/                     общий ядро (чистый JS ESM, используется расширением и CLI)
  terminals/             адаптеры терминала (wezterm; см. docs/TERMINALS.md)
  platform/windows/paths/liveness/members/claims/plan/preflight/discover/
  launch/spawn/verify/restore/cli/prune/health/inuse/pane/sessions/i18n/version
bin/pi-reopen.js         точка входа CLI (запускается напрямую node, без шага сборки)
test/                    встроенные тесты Node (изолированные каталоги + инжектируемые моки, без реальных вызовов терминала)
docs/                    требования, статус, платформы, терминалы, публикация
```

Тесты покрывают базовое восстановление, порядок обработки сигналов, очистку при reload, детект закрытия по панелям, подбор `/reopen recent`, нестандартные пути установки Pi, shell-экранирование, слияние записей из устаревшего каталога, версионирование схемы, i18n и загрузку после переноса пакета; тесты изолированы временными каталогами и моковым лаунчером. Тестовый хук `PI_REOPEN_HOOKS` не следует задавать в обычном использовании.

CI выполняет платформенный набор на Linux/macOS/Windows, полный набор на Linux, проверку упакованного tarball и реальный цикл жизни PTY Pi (устанавливает хост Pi). CI не может открыть GUI WezTerm, поэтому реальный тест spawn/заголовка остаётся опциональным через `PI_REOPEN_INTEGRATION=1`.

Шаги релиза для мейнтейнеров: см. [гайд по публикации](docs/PUBLISHING.md) и [CHANGELOG](CHANGELOG.md).
